# ADR 0020：忙碌查询排队，不以并发数量拒绝业务请求

状态：Accepted

同一用户打开多个预览或刷新图表时，旧 API 将 queued 与 running 都计入每用户 2 个、组织 8 个在途上限，立即返回 429 QUERY_CAPACITY_EXCEEDED。单个 iframe 排队无法协调其他页面、工具和取消尚未完成的查询，因此此前只做页面排队不足以解决问题。

合法且已授权的查询直接持久化为 queued，不按用户或组织在途数量拒绝。后台依据实际运行槽位调度：按用户排序等待队列，只选择当前有执行位置的任务；运行位置不足时仍留在队列。租约在事务内重新校验权限、组织、环境和状态，忙碌返回签名 null，不递增 attempt 或失败任务。worker 已忙碌时返回签名 queued 回执；调度器随后重试，不把忙碌归为依赖故障。数据库池忙碌也回到 queued，且不消耗失败尝试次数。

执行侧仍按连接和 worker 的实际能力依次运行；这些是内部调度位置，不是用户必须减少图表数量的产品配额。权限撤销、取消、查询超时和真实依赖中断仍有明确终态；不关闭数据权限验证。

网页和插件默认等待队列取消 64 项数量拒绝。预览持续轮询至服务器终态或用户取消，不以固定 120 次轮询将等待误报为查询超时。父页面每 5 秒向有效等待请求发送 studio.pending；新版 runtime SDK 按活动心跳维持桥接响应，不让排队时间消耗无响应检测时间。旧不可变产物仍使用旧 SDK 的自身超时；后端接收和排队对旧版本立即生效，新心跳行为需要重新构建版本。

按用户要求，本次只编译、更新运行服务并安装插件 0.1.9，不执行自动化、浏览器或 Harness 测试。新增并发接收、实际运行/等待状态和取消回归用例尚待执行，不能以此前通过数表示本次通过。
